# Alloyによる形式検証の実習

## 検証対象のOSS
本レポートでは，オープンソースのSQLリレーショナルデータベース管理システムであるMySQLを対象に検証を行った．MySQLは，データベース操作言語であるSQLを実用の上で扱えるように様々な機能を備えたRDBMSの一種である．ソフトウェアとしての規模が大きく，システム全般について考えるのは非常に困難なため，ごく基本的な次の2つの側面のみに抽象化して考えることとする．
* リレーショナルベース(以下RDB)に基づくデータベース構造
* ACID特性を満たすように設計されたトランザクション操作

本レポートにおいては，それぞれの観点別にモデル化しその性質を検証する．

## 検証すべき性質
### 1. MySQLのデータベース構造に関する性質
MySQLの使用を含めRDBは，利用者が「当然の前提」としている多くの性質の上広く利用されている．しかしそれらの性質は必ずしも定義から自動的に保証されるとは限らないと考えた．  
そこで本レポートでは，実際のデータベース利用において暗黙に期待されている振る舞いを「性質」とみなし，それらが本モデルにおいて本当に保証されているか，一部のごく基本的な要素を取り上げAlloyを用いて検証する．

#### 性質1: 「テーブル，列，およびレコードが与えられれば，対応する値は一意に定まる」
この性質はRDBの定義から直ちに導かれる自明な性質である.
しかし，Alloy によるモデル化においては，値の対応関係が曖昧なままでも一見すると整合的なインスタンスが生成されてしまう可能性がある．  
そのため本研究ではモデルが意図した決定性を満たしていることを確認する目的で，本性質を検証対象とした．

#### 性質2: 「主キー制約の下では，主キーの取る値はテーブル内のレコードを一意に識別する」
主キーは，NULLを許さずかつ同一テーブル内で値が重複しないという条件をもつ特殊な列である．
ここで，主キーとしてある値をもつレコードは一意に識別されるという暗黙的な性質を検証する．
* 一般的な具体例）  
「学生管理」テーブルにおいて，「学生番号」を指定すれば，対応する学生の情報がただ一人分得られると期待する．

#### 性質2(+): 「ユニークキー制約では主キーと同様の識別性は必ずしも成立しない」
ユニークキーは，値がNULLでない場合は値の重複が許されないが，NULL値を持つ複数のレコードが存在することは許される．この違いにより性質2がユニークキーでは必ずしも成立しないことを検証する．
* 一般的な具体例）  
「連絡先」テーブルにおいて，「マイナンバー」を指定すれば人物がただ一人に特定できるが，マイナンバーが未登録(NULL)の人を一人に絞ることはできない．

#### 性質3: 「外部キー制約の下では，各レコードの外部キー値は，他テーブル上のいずれか一つのレコードの主キー値を参照する」
外部キーは他テーブルの主キーをもとに値を参照する目的で存在する特殊な列である．
主キーと同じく暗黙的な性質で，外部キーを持つレコードは，その値を用いていずれかの他テーブルのレコードを参照できるという性質を検証した.
* 一般的な具体例）  
「製品」テーブル上の「製造所ID」が「製造所」テーブルを参照している場合，各製品には必ず実在する製造所が対応していると期待する．


なお本来のMySQL使用ケースでは主キーではないユニークキーの参照も行うが，今回は簡単のため主キーのみに限定して考えることとする．

## モデル化
データベーステーブル(以下テーブル)は，一般的には行(レコード)と列（フィールド）からなる二次元配列として捉えられることが多い．今回モデル化するにあたってはテーブルを，固有の列要素の集合，およびレコードの集合からなる構造体と捉える．  

### 基本的な構造のモデル化
まず，RDBMSにおけるテーブル，列，レコードといった基本構造をAlloyのsigと関係によって直接的に記述した．
キー制約については考えない基本的な構造をモデル化したalloy-rdb.alsを参照しながら説明する．

| Aloy | 意味 | MySQLにおける対応 |
| ---- | ---- | ---- |
| sig Table | テーブル(データベース) の概念 | TABLE |
| sig Colmun | 列・フィールド | COLUMUN |
| sig Record | 一行のデータ | レコード |
| sig Value | 列に格納される値 | カラム値 |
| sig NUull | Null値 | NULL |

その上で各概念の関係性を以下のように記述することによって役割を再現する．
| Aloy | 意味 |
| ---- | ---- |
| Record.table: one Table | 行は必ず1つのテーブルに属する |
| Column.table: one Table | 列は1つのテーブルに定義される |
| Record.values: Column -> one Value | レコードは，列に対応する値を一つとる |

ここでValueはNullも含むので，`lone Value`は値を何もとらないということを意味する．
しかしMySQLでは値の未定義は許容されないため，factにより次の制約条件を加える必要がある．

| Aloy | 意味 |
| ---- | ---- |
| fact RecordUsesTableColumns | 全てのレコードで，値に紐ずく列はテーブルに定義されている列に含まれる |

この制約について，詳しくは検証の1に記載する．

### 各キーの制約のモデル化
性質2,3の検証にあたって，上記の基本的な構造に追加し，いくつかのキー制約について形式化する． 
最初にキー制約に関する概念の構造と最小限のfact制約のみ下記に記載する．  
補足するとMySQLおよびRDBでは，各キーについて，テーブルに必ず1つ以上存在するという条件は存在しない．
しかしそれぞれの性質を調べるにあたって，各キーが存在する場合のみ考えるという前提を明示的に与える役割で「〇〇Exsists」というfactを設定している．
